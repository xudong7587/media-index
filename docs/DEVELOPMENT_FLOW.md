# MediaIndex 开发分支、测试、部署与合并流程

这份文档是日常开发的默认流程。目标是让用户只给一个大致功能方向，Codex 先整理任务书、一次性完成主要实现、快速部署到自用 NAS 版，并把用户验收压力降到“打开看看核心路径是否符合预期”。

## 新会话入口

- 开始开发、测试、部署或合并前，先读 `AGENTS.md` 和本文件；本文件是流程权威，`AGENTS.md` 是入口摘要。
- 默认按“任务书 -> 大块实现 -> 针对性验证 -> NAS 部署 -> 线上冒烟 -> 用户验收”推进，不要每改一点就要求用户手测一点。
- 只有完成当前源码同步、远端本地镜像构建、`media-index` 容器重建、页面可打开、本次功能入口冒烟，才能说“已部署到自用 NAS”。
- 只改本地代码、只打源码包、只改 `VERSION` / `frontend/package.json`、只跑测试或只跑前端构建，都必须汇报为“未部署”或“仅本地完成”。
- 自用 NAS 临时版本号可以用 `0.5.1-test1` 这类后缀帮助用户识别，但版本号不是部署证据；最终汇报仍要写清 NAS 容器镜像/版本、页面和功能入口验证结果。

## 角色分工

- 用户负责提出目标、边界和最终验收感受，不负责逐项陪测。
- Codex 负责拆任务、实现、选择验证强度、部署、冒烟检查和汇报风险。
- GitHub PR/CI/Release 是正式发布流程；自用 NAS 部署是日常验收流程；二者不能混为一谈。

## 默认闭环

1. **收口需求**：把用户的一句话想法整理成 `leader` 风格任务书。能从代码、文档、命令或联网查到的信息先自己查，只问会改变方向的问题。
2. **开分支**：所有开发从非 `main` 分支开始。分支名建议 `feature/<short-topic>`、`fix/<short-topic>` 或 `chore/<short-topic>`。
3. **先做大块实现**：按任务书一次完成主要后端、前端、文档和配置改动；避免每改一点就让用户手测一点。
4. **针对性验证**：根据改动面选择最小有效测试，不用“几百个测试通过”冒充真实可用。
5. **部署到自用 NAS**：日常验收优先部署当前源码到 `https://media.dunn.fun:666/`，不等待 GitHub/GHCR。
6. **线上冒烟**：部署后由 Codex 先检查容器、页面、静态资源、日志和本次功能入口，再让用户验收。
7. **用户验收**：用户只看核心体验和结果是否符合预期；发现问题后 Codex 继续修同一分支。
8. **PR/合并/发布**：用户确认后再决定是否推 Git、开 PR、等 CI、合并 `main`、打 tag 和发 Release。

## 三档验证

### A. 快速功能分支

适用：前端展示、小型后端逻辑、配置项、文案、窄范围 bugfix。

必须做：

- `git status -sb`
- 阅读受影响文件和相邻调用链。
- 跑与改动直接相关的单测或类型检查。
- 如改前端，至少跑 `pnpm --dir frontend build`，除非只是文档或用户明确要跳过。
- 部署到 NAS 后做线上冒烟。

可不默认做：

- 本地整仓 Docker build。
- 全量后端测试。
- GitHub Actions/GHCR 等待。

### B. 风险功能分支

适用：任务调度、转存、追更、路径生成、数据库迁移、认证、安全、通知、多 provider 状态、部署脚本。

必须做：

- A 档全部项目。
- 跑相关测试文件，并补缺失的回归测试。
- 跑全量后端单测：`$env:PYTHONPATH='backend'; .\.venv\Scripts\python.exe -m unittest discover -s tests`
- 前端构建：`pnpm --dir frontend build`
- NAS 部署后检查容器日志和真实功能入口。

按风险追加：

- Docker 镜像构建：`docker build -t media-index:local .`
- 只读生产数据 dry-run：`python scripts/integration_dry_run.py`，仅在任务命中搜索、识别、追更链路且环境允许时使用。

### C. 正式发布

适用：用户明确要求“推送到 Git”“合并入 main”“发布版本”“发 Release”。

必须做：

- B 档全部项目。
- 更新 `VERSION`、`frontend/package.json`、`README.md`、`CHANGELOG.md` 和必要使用文档。
- 创建 PR，通过 GitHub Actions 必需检查。
- 用户明确授权后才合并。
- 合并后确认 Docker/GHCR workflow、版本 tag、GitHub Release。
- 单独汇报 NAS 是否已部署；合并成功不等于 NAS 已更新。

## 测试口径

- 测试数量只能作为覆盖范围参考，不能当作功能可用证明。当前仓库约有 262 个 `def test_` 测试函数；它们主要覆盖后端逻辑，不等于浏览器、NAS、第三方服务和真实配置都可用。
- 最终汇报必须写清“跑了哪些命令、覆盖了什么、没覆盖什么、线上冒烟看到什么”。
- 禁止为了绿灯而 skip/todo、放宽断言、mock 被测对象、删测试、改阈值、改验收脚本或追加 `|| true`。
- 对用户可见功能，至少要有一个真实入口验证：页面能打开、按钮/API 能到达、错误能被看见或日志能说明。

## NAS 部署规则

- 日常小改动也使用完整源码包或完整 staging，同步到 NAS 后在远端构建本地镜像；不要只上传少数增量文件。
- 不用 PowerShell 文本管道传二进制包；优先 `.tar.gz` 文件上传，避免转码和路径层级问题。
- SSH 必须显式使用本机密钥 `~/.ssh/codex_media_index_nas_ed25519`、`BatchMode=yes` 和 `IdentitiesOnly=yes`，不要依赖 SSH 自动选钥匙。NAS 已配置 `Sunnydunn` 对 `/usr/local/sbin/media-index-deploy` 的 sudoers 免密白名单，常规重建容器应优先调用 `sudo -n /usr/local/sbin/media-index-deploy`，不要再向用户索取 sudo 密码。
- 如果免密部署脚本不存在、失效或不覆盖当前任务，才说明原因并询问用户是否临时提供 sudo 密码；一次部署最多询问一次，且不能把密码写进文件、日志或回复。
- 如果 sudo 权限缺失导致无法重建容器，Codex 只能完成本地代码和源码包准备，并明确标记“未部署”，不能说已上线。
- 自用 NAS 远端 `docker-compose.yaml` 是运行配置，不能用仓库公共模板覆盖；远端 `data/`、`.env`、数据库和下载目录不得覆盖或删除。

## Token 和沟通预算

- 开工前只做必要调研，不把大段文件、完整测试输出和重复日志贴给用户。
- 中途更新只汇报新发现、阻塞和阶段结果；没有新信息不重复播报。
- 每次功能开发以一个分支、一个任务书、一个验收清单推进，避免把同一目标拆成十几轮碎片确认。
- 发现方向错了、验收连续失败 3 次、或部署环境缺权限时，先止损并说明选择，不继续空转。
